# 開發日記

這份日記記錄這個專案從開始到現在的演進：每一步為什麼這樣走、學到了什麼。它是給未來回看用的敘事，所以只寫脈絡與決定，**不含任何真實數值、參數或遊戲資產**。逐條的判斷見 [`decisions-log.md`](decisions-log.md)，commit 細節見 git log。

## 2026-11-02 · 第一步：自己蓋一套探索工具與 MCP

**起點**：想在課程的商業模擬遊戲中做出有依據的決策，而不是憑感覺。第一個念頭是把遊戲的前端「讀懂」：哪些畫面、哪些服務呼叫、哪些計算是在客戶端做的。

**做法**：原本想用現成的逆向工程工具 REA，但當時本機的 Node.js 跑不起來，所以用 Python 自己重寫了一部分：
* HAR、HTML 解析，以及用正規表示式掃描 JavaScript 符號；
* 從客戶端程式碼找出「看起來是公式」的片段；
* 包成一個有 22 個工具的 stdio MCP 伺服器，讓 agent 能查詢。

**回頭看**：這一版跑得起來，但它是「自己再造一個逆向工具」，準確度和維護成本都不理想。它產出的客戶端符號索引、公式片段等檔案也一路留在歷史裡，後來成為歷史清除要考慮的一部分。

## 2026-11-03 下午 · 轉向 REA

**轉折**：Node 環境問題解決後，改用 REA 本身當逆向工程與證據層。REA 本來就是 MCP 伺服器，沒有理由再維護一套自製的。

**做法**：
* 自製工具整包搬到 `legacy/`，標記為停用，但保留下來做比較，將來也可能再串回 MCP。
* 新增 REA Evidence 的匯入，整理出決策、指標、RPC 三份目錄，以及實驗手冊。

**學到的**：「保留舊東西做對照」很有價值，但要清楚標示它的地位，免得新舊混用。

## 2026-11-03 傍晚 · 成本面驗證（以及外洩的起點）

**目標**：先驗證最確定的部分，也就是成本與會計規則。這些在遊戲裡有「試算」畫面，可以只讀、不送出地觀察輸入與輸出的關係。

**做法**：
* 一連串實驗：存款利息通道、固定產能選項、開設銷售據點與網路中心等。
* 用一個「守門員」限制只能做純檢視的動作，並把每個判斷記入決策日誌。
* 從觀察中抽出參數，建立第一個**已驗證（verified）**的成本模型。

**出錯的地方**：實驗文件與一個測試檔把觀察到的**真實數值**直接寫進公開檔案，而且已經 push。當時的檢查只看檔名與明顯的敏感字樣，沒抓到數值本身。

## 2026-11-03 晚間 · 開放引擎 + 私有資料

**想法**：真正想要的是一個「可以在本機反覆試玩」的模擬器。但直接做一個特定商業遊戲的複製品不對，所以把它設計成**通用、資料驅動的經營模擬引擎**：
* 引擎與規則公開，模組名稱通用；
* 真實參數只放在 `evidence/private/`，不進 repo；
* 公開範例只用虛構（synthetic）參數包。

**同時補上的防線**：publication gate 加入「真實數值外洩」偵測，拿私有的真實值去比對每個要公開的檔案。它第一次跑就抓到前面那幾個 commit 的外洩。當時的處理是**清掉現有檔案、不改寫歷史**。這留下了一個隱患：最新版本乾淨了，舊 commit 還在。

## 2026-11-03 晚間 · 控制平面

在引擎外面加一層「控制平面」，讓人與 agent 都能操作：
* 情境（參數覆寫、事件、對手設定）、壓力測試 sweep、參數包之間的 diff；
* HTML 報告、CLI 與 MCP 介面；
* 每季的參數快照與自動 diff 流程。

**原則**：所有計算都走同一個引擎，控制平面只負責組合與呈現。

## 2026-11-03 晚間 · 需求面：用公開文獻補上函數形式

**問題**：成本面可以驗證，需求面卻沒有可觀察的試算通道，原本只能用佔位（placeholder）公式。

**做法**：只採用公開發表、可引用的行銷與經濟學文獻：
* 多項 logit 選擇、廣告商譽的累積與遞延、通路覆蓋等函數形式；
* 係數取文獻中間值，並標註為新的來源等級 **literature**。

來源等級變成：verified > derived > estimated > literature > placeholder。組合出來的數字一律取最弱的等級。

**刻意不做的**：任何別人擷取或貼出的遊戲數據、論壇數字，一律不用。需求要升為 estimated，必須等本局資料累積、擬合並通過留出季驗證。

## 2026-11-03 深夜 · 發現歷史外洩，先調查、不動手

**發現**：在做 UI 的途中確認到 repo 是**公開**的，前面那 4 個含真實數值的 commit 都在 GitHub 上。

**選擇**：只調查與寫計畫，不改寫歷史。
* 掃描全部歷史，確認外洩範圍只有那 4 個 commit、4 個檔案；沒有帳密、cookie、截圖或遊戲資產檔。
* 寫好 filter-repo 的清除計畫、替換檔產生器與驗證腳本，全部標註「待使用者在場時執行」。
* gate 補強：能抓「由真實費率推導出的值」；可以逐一掃描每個要 push 的 commit，而不只是最後狀態。

**學到的**：「先洩漏、後清除」在 git 裡不算清除。檢查必須作用在每一個 commit 上，而且要在 push 之前。

## 2026-11-03 深夜 · Web UI

**目標**：把引擎變成看得見、點得到的工具，同時讓「哪些數字可信」一眼可見。
* FastAPI 薄層 API，只綁本機，只呼叫既有引擎；
* React 前端有兩種資料來源：虛構結果的靜態 demo，以及連本機 API 的實戰模式；
* 每個數字都標出來源等級；文獻或佔位等級的數字加上「未校準 · 非預測」標記，滑鼠移上去可以看到完整來源鏈。

**邊界**：demo 只用虛構資料，gate 也會檢查前端建置產物。GitHub Pages 的發布是手動的，而且被歷史清除擋在後面。

## 2026-11-04 · 歷史外洩的處理決定：先留存，之後一次清除

**決定**：**暫不清除歷史**，改為：
1. 把外洩內容完整匯出到 `evidence/private/leak-archive/`：各 commit 外洩檔案的原樣、`legacy/` 的快照、整個歷史的 bundle，再加一份索引。這樣將來就算清掉歷史，本機仍查得到；
2. 立一個置頂待辦 [`TODO-history-cleanup.md`](TODO-history-cleanup.md)，寫明三條硬約束：清除前不得改回 public、不得上 Pages、清除方案與留存的位置；
3. 加一道自動提醒：只要待辦還沒標成已清除，建置 dist、發布 Pages、準備公開，或 repo 處於公開狀態時 push，都會響鈴警告；Pages workflow 則直接失敗。

**理由**：課程還在進行，歷史與 `legacy/` 還有查詢與思考的價值；改寫歷史不可逆，最好在「遊戲結束、確定要公開」時一次做完。在那之前，風險由 repo 維持 private 擋住，而提醒機制負責防止忘記。

**還沒解決的**：公開歷史仍含外洩內容。這件事沒有消失，只是被延後，而且被明確地標記與看守。

## 貫穿全程的幾條心得

* **一個引擎**：所有介面（CLI、MCP、API、UI）都呼叫同一套計算，避免結果分歧。
* **來源等級誠實**：數字標到它真正有的可信度，不多也不少。
* **公開與私有的邊界要靠機器守**：靠記性一定會漏，所以要有 gate、hook 與提醒。
* **不可逆的動作留給人在場時做**：改寫歷史、force push、公開 repo 都是如此。
