# VeloForge Q1 → Q2: Sales-led capacity bridge

This is an **offline planning aid**, not Marketplace's proprietary PHP engine. It reads the team's own local HAR in memory. Neither the script nor the MCP server saves game decisions or advances a quarter.

## Ownership and operating sequence

1. **Sales** estimates demand *by actual existing brand* and confirms pricing, advertising, store/web staffing, and the sales forecast.
2. **Manufacturing** receives those forecast units and sizes an *indicative* daily operating capacity; checks the game's real factory simulation before approving it. Do not buy more printers merely because fixed capacity is available.
3. **Finance** reruns the Q2 factory simulation at 100%, 50%, and 25% of the Sales forecast and loads each scenario into **Pro Forma Cash Flow**. Normal ending cash target ≥500,000; 50%-demand target ≥300,000; 25%-demand case must be survivable.
4. **President** reviews the completed decision checklist before final submission. No submission is performed by code.

## Missing elements now addressed

- Distinguish **Q1 final bank cash** from a **Q2 draft pro forma** and a separate **Q2 factory simulation** snapshot. Different snapshots do not imply financial performance changes.
- Keep Q1 **certificate of deposit** separate from immediately spendable bank cash, unless the game records a withdrawal.
- Build a cash bridge from actual Q1 cash and Q2 **currently observed** financing, channel cost, interest, and other known flows; compare against the Q2 simulated cash number and flag any mismatch.
- Do not treat a Q2 capture with zero Sales staff, demand and operating capacity as a zero-sales forecast. The forecast is **missing**, not estimated at zero.
- Preserve **brand-specific cost quotes** at each server-observed volume level, with no claim to reconstruct the cost formula.
- Keep capacity as a clearly labelled heuristic until actual daily capacity / workday productivity / changeover / overtime are validated by the factory engine.
- Require observed cash in all three demand scenarios before declaring the teacher's cash guardrails met.

## Local execution

Install the repo in editable mode as described in README. Keep the user's raw HAR under ignored \`evidence/private/\`.

\`\`\`bash
python scripts/q2_quarter_bridge.py --har evidence/private/q2_capture.har --output evidence/private/q2_reconciliation.json
\`\`\`

After Sales finishes the forecast, save \`evidence/private/sales_forecast.json\`. The following names/values are **synthetic examples only**:

\`\`\`json
{"brand_demand":{"Example Mountain A":30,"Example Mountain B":30,"Example Speed A":20,"Example Speed B":20}}
\`\`\`

\`\`\`bash
python scripts/q2_quarter_bridge.py --har evidence/private/q2_capture.har --sales evidence/private/sales_forecast.json --output evidence/private/q2_planning.json
\`\`\`

The script uses 65 working days per quarter as a planning assumption. The observed productivity percentage is applied to capacity heuristically and must not be presented as an exact Marketplace formula. \`maximum_daily_capacity\` is obtained from the observed Q2 \`OperatingCapacity\` view. For each demand scenario, the script returns an unadjusted required daily slot count, an illustrative productivity-adjusted slot count, and whether the latter is below the observed fixed capacity.

After running the simulator and reloading Pro Forma Cash Flow separately for each demand scenario, record **actual observed** cash figures in \`evidence/private/observed_cash.json\`. The example below is synthetic:

\`\`\`json
{"most_likely":510000,"pessimistic_50pct":320000,"worst_case_25pct":150000}
\`\`\`

\`\`\`bash
python scripts/q2_quarter_bridge.py --har evidence/private/q2_capture.har --sales evidence/private/sales_forecast.json --cash evidence/private/observed_cash.json --output evidence/private/q2_final_review.json
\`\`\`

## Sources and limitations

| Field | Exact evidence | Interpretation |
| --- | --- | --- |
| Q1 bank cash | \`CashFlow.view.staticData.sections\` | **Actual** settled quarter |
| Q1 certificate of deposit | \`BalanceSheet.view.staticData.sections\` | Separate cash-equivalent asset |
| Q2 financing/cost/interest | \`ProFormaCashFlow.view.dynamicData.items\` | **Current captured decision inputs**, not a completed quarter |
| Q2 factory cash | \`ExtFactorySimulation.view.calculate.accounting.cash\` | **At captured simulation state**, not proof all decisions are completed |
| Q2 pro forma cash | \`ProFormaCashFlow.view.calculate.items\` | May be stale / not reloaded after decisions |
| Per-brand unit cost quote table | \`CostOfProduction.view.dynamicData.brands[].cogsEstimates\` | Observed quote points only; no extrapolation |
| Sales forecast | Team-supplied local JSON | Not generated by the simulator when input is still blank |
| Required daily capacity | Local planning envelope | Heuristic, not the game's PHP formula |
| Three cash risk gates | Three newly rerun pro forma observations | Measured, not estimated by local model |

Do not conflate Q1 loss with Q2 operating cash, or assume a noncash Q2 net income value can be derived solely from visible cash transactions: depreciation, accruals and other rules may remain opaque.

## Safety and stop rules

Raw HTML/JS/HAR, session tokens, cookies, IDs, and game payloads must stay in ignored \`evidence/private/\`. Public source and test fixtures are synthetic. No credentials or actual game response values should be committed.

**Block factory approval** if Sales has not sent brand-level demand. **Block Q2 financial signoff** if any one of the 100%, 50% or 25% scenario cash results is absent; inspect why if the 50% ending cash is below 300,000. Only the team makes live game decisions.
